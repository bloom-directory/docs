# Petals :badge[Partial]{warning}

A Petal is a local, off-chain package that adds new files to walletFS. It
contains a filesystem-shaped tree of routes, each compiled to its own
WebAssembly component, plus a manifest that declares exactly which host
authority the package is allowed to use. Bloom mounts the tree read/write under
`/petals/<name>/`, so agents and people work with a Petal the same way they
work with the rest of walletFS: `ls`, `cat`, and write a file.

Petals do not run on a chain, are not called through transaction blocks, and
have no object model of their own. Everything a Petal can reach — HTTP, storage,
signing, key derivation, the transaction outbox, chain reads, walletFS itself —
is an explicit capability mediated by Bloom.

## Why this shape

- **Reviewable.** A route's behavior is visible in the single source file that
  compiles to that route's component. There is no central dispatcher to trace.
- **Least authority.** Route metadata, the package manifest, and the compiled
  component's imports are three separate scopes that must agree. Metadata can
  narrow authority at runtime; nothing can widen it.
- **No custom signing or broadcast code.** A Petal describes an intent; Bloom
  owns approval, signing, and submission.
- **Deterministic to ship.** Packaging produces byte-identical archives, and
  releases are pinned by tag, commit, archive name, and package hash.

## The route tree is the interface

A package holds exactly one route tree. Its layout on disk is its public
filesystem:

```text
my-petal/
  petal.toml            # identity, consent summary, capability ceiling, policy
  README.md             # developer/contributor documentation
  AGENTS.md             # operating contract for users and agents
  petal/
    my-petal/           # must match `name` in petal.toml
      $index.wasm       # the directory itself
      status.json.wasm  # /petals/my-petal/status.json
```

Every route artifact is a WebAssembly component implementing the
`bloom:route@0.1.0` contract; raw core Wasm is rejected. The contract exports
`metadata`, `lookup`, `list`, `read`, and `write`, and a route returns
`route-error.unsupported` for anything it does not implement.

## Writes are not completions

A successful write means the route handler completed. It does not mean a
transaction was approved, broadcast, or confirmed. Petals must expose those
states explicitly through inspectable routes and receipts. See
[Writes and receipts](/petals/ptbs-and-pipes).

## Toolchain

| Tool | Owns |
| --- | --- |
| `petal` CLI (`bloom-petal-cli`) | `new`, `build`, `check`, `package`, `inspect` |
| `bloom petals` | `build`, `install`, `ls`, `uninstall` — package validation and installation |
| `bloom vfs` | direct read/write against the mounted tree |

The `bloom-directory/petal` repository is the release authority for the
component contract, the Rust SDK (imported as the crate `petal`), the route
builder, the CLI, templates, and conformance fixtures.

## A real example

[`bloom-petal-hyperliquid`](https://github.com/bloom-directory/bloom-petal-hyperliquid)
is the reference production Petal. It exposes read-only market and account
files, signed exchange actions, owner-approved USDC transfers, and bounded
agent sessions under `/petals/hyperliquid/`. All HTTP access, persistence, and
signing go through Bloom's authority path; bounded agent private keys stay
exclusively in Signer and are never generated by, returned to, or stored by the
Petal.
