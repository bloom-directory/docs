# Petal Model :badge[Partial]{warning}

A Petal is a package of WebAssembly components mounted into walletFS. This page
describes the contract those components implement, how Bloom resolves a path to
a component, and how authority is granted.

## Pieces

| Piece | Meaning |
| --- | --- |
| Package | A directory with `petal.toml`, `README.md`, `AGENTS.md`, and exactly one route tree under `petal/<name>/`. |
| Route | One `.wasm` component implementing `bloom:route@0.1.0`, bound to one path in the tree. |
| Manifest | `petal.toml`: identity, consent summary, capability ceiling, and per-surface policy. |
| Route metadata | The `route-meta` a component returns from its `metadata` export; the runtime narrowing boundary. |
| Mount | `petal/<name>/` is served at `/petals/<name>/`. |
| Package hash | Content hash of the deterministic package, used to pin an install. |

## The route contract

Every route artifact is a component implementing `bloom:route@0.1.0`. Raw core
Wasm is rejected. This is the canonical
[`route.wit`](https://github.com/bloom-directory/petal/blob/main/wit/route/route.wit):

```wit
package bloom:route@0.1.0;

interface types {
  record ctx {
    petal-root: string,
    package-hash: string,
    path: string,
    params: list<tuple<string, string>>,
    actor: option<string>,
  }

  enum entry-kind { dir, file, symlink }

  record entry {
    name: string,
    kind: entry-kind,
    mode: u32,
    size: option<u64>,
    link-target: option<string>,
  }

  record route-meta {
    kind: entry-kind,
    mode: u32,
    cache-ttl-ms: option<u64>,
    side-effecting-read: bool,
    write-async: bool,
    description: option<string>,
    consent-summary: option<string>,
    required-caps: list<string>,
    sign-intent: option<string>,
    executable: bool,
  }

  variant route-error {
    not-found(string),
    not-a-dir(string),
    denied(string),
    invalid(string),
    backend(string),
    unsupported(string),
  }
}

world route-file {
  use types.{ctx, entry, route-error, route-meta};

  import bloom:http/fetch@0.1.0;
  import bloom:store/kv@0.1.0;
  import bloom:key/derive@0.1.0;
  import bloom:sign/signing@0.2.0;
  import bloom:tx/outbox@0.1.0;
  import bloom:chain/read@0.1.0;
  import bloom:vfs/readwrite@0.1.0;
  import bloom:env/runtime@0.1.0;
  import bloom:private-input/ceremony@0.1.0;

  export metadata: func(ctx: ctx) -> result<route-meta, route-error>;
  export lookup: func(ctx: ctx) -> result<entry, route-error>;
  export %list: func(ctx: ctx) -> result<list<entry>, route-error>;
  export read: func(ctx: ctx) -> result<list<u8>, route-error>;
  export write: func(ctx: ctx, body: list<u8>) -> result<_, route-error>;
}
```

Return `route-error.unsupported` for operations a route does not implement. A
normal file route is readable by default; a route that advertises write access
must export `write`.

The `bloom-petal-contract` crate embeds this WIT and exposes contract IDs,
capability mappings, and a deterministic WIT digest. `petal inspect` prints the
digest your toolchain speaks. Consumer CI should reject a digest it did not
intentionally upgrade to.

## Route tree resolution

The route tree on disk *is* the public VFS declaration. Filenames determine
paths:

| Source file | Route |
| --- | --- |
| `status.json.rs` → `status.json.wasm` | the file `/petals/example/status.json` |
| `$index.rs` → `$index.wasm` | the containing directory (`lookup`, `list`, `read`) |
| `$lookup.rs` → `$lookup.wasm` | refines `lookup` for dynamic entries |
| `[wallet]/balance.json.rs` | binds a dynamic `wallet` parameter |

Rules:

- Static segments take precedence over dynamic segments.
- Reserved `$...` names are only valid as recognized special route leaves.
  `$list` is not one of them; use `$index`.
- A bracketed segment such as `[slug]` is read with `petal::param(ctx, "slug")`.
- Directory contents are explicit. Listing a dynamic directory does not happen
  automatically — an `$index` route must produce the child list.

A route may also have a sibling `.route.toml` sidecar pointing at a primary
component under `modules/` or `components/` with dependencies under
`components/`.

## Authority

Authority is declared in three distinct scopes, and they must agree:

1. **Compiled imports.** What the component actually imports — the hard ceiling.
2. **Route metadata `required-caps`.** What that one route intends to use at
   runtime.
3. **`petal.toml`.** The package-wide ceiling in `[caps].allowed`, plus
   per-surface policy in `[[net.allow]]`, `[store]`, `[sign]`, and
   `[[key.derive]]`.

Metadata may narrow installed authority at runtime but may never widen it.
Bloom grants only the narrowed set, so any omitted host surface must be
unreachable on the successful path.

Imports map to capabilities as follows:

| WIT import | Manifest capability or policy |
| --- | --- |
| `bloom:http/fetch@0.1.0` | `bloom:http` plus `[[net.allow]]` |
| `bloom:store/kv@0.1.0` | `bloom:store` plus `[store]` namespaces |
| `bloom:sign/signing@0.2.0` | `bloom:sign` plus `[sign].allowed_intents` |
| `bloom:key/derive@0.1.0` | `bloom:key.derive`, plus `[[key.derive]]` for delegated operation classes |
| `bloom:tx/outbox@0.1.0` | `bloom:tx.outbox` |
| `bloom:chain/read@0.1.0` | `bloom:chain` |
| `bloom:vfs/readwrite@0.1.0` | `bloom:vfs.read` and/or `bloom:vfs.write`, per the functions used |
| `bloom:env/runtime@0.1.0` | no additional capability |

Policy structures reject unknown fields. Network paths must be explicit: write
`"/*"` deliberately rather than relying on an empty list, and never rely on a
wildcard host. `[[net.allow]]` may also name a configured endpoint with
`binding = "..."`.

A representative manifest:

```toml title="petal.toml"
schema = "bloom.petal.package.v1"
name = "example"

[consent]
summary = "Read an API and store package-local state."

[caps]
allowed = ["bloom:http", "bloom:store"]

[[net.allow]]
host = "api.example.com"
methods = ["GET"]
paths = ["/v1/*"]

[store]
namespaces = ["cache"]
secret_namespaces = ["credentials"]
```

### Signing and derived keys

A package declaring `bloom:sign` must list allowed intents, and each signing
route's metadata must select one of them. The retired hash-only
`bloom:sign/signing@0.1.0` import is incompatible with production signing and
fails closed; `bloom:sign/signing@0.2.0` carries the exact payload, an optional
Signer-owned Petal `KeyRef` selector, and atomic ordered batches.

Child-key operation classes are distinct from the signing intent a route uses
immediately. Declare each delegated class on the exact route pattern that
imports `bloom:key/derive@0.1.0`:

```toml
[[key.derive]]
route = "[network]/agent_sessions/[wallet]/new.json"
operation_classes = ["venue.agent_action"]
```

Every listed class must also appear in `[sign].allowed_intents`. Bloom rejects
unknown or duplicate routes, empty or duplicate class lists, invalid class
tokens, and declarations on routes without the key-derivation import. The
installer records only the route's immediate signing intent and these explicit
delegated classes; other package-level signing intents are not inherited.

### Secrets

Private keys, derived agent keys, API secrets, bearer tokens, secret-store
values, and replayable or not-yet-submitted signatures are confidential. Keep
them in the store's secret namespace and never copy their bytes into the public
state namespace, errors, logs, or a read response. Treat signature bytes as
confidential unless the product contract explicitly classifies a finalized
signature as public.

## Validator boundaries

Different tools check different things, and none of them checks everything:

- `petal build`, `petal check`, and `petal package` reject a capability
  declared by a route spec that the compiled component does not import, and
  reject unknown component imports.
- `petal package` validates only basic `petal.toml` identity. It does not prove
  the complete manifest policy covers compiled imports.
- `bloom petals build` and install validation reject compiled imports not
  covered by `[caps].allowed` and the applicable network, signing, and store
  policy, and enforce route metadata as a runtime narrowing boundary.
- The Petal CLI treats a VFS interface import as both VFS capabilities when
  checking a route's declared ceiling; Bloom's package validator performs the
  finer used-function inference. Confirm final policy with Bloom rather than
  inferring it from the interface name.

## GitHub source packages

A source repository may declare a build:

```toml
[source]
kind = "github"
repository = "bloom-directory/bloom-petal-example"

[build]
command = "./scripts/build-package"
outputs = ["artifacts/routes"]
```

Bloom executes that command natively with the installing user's privileges.
Publishing under a trusted owner is therefore an assertion about the
repository's source, build script, and dependencies — not only the resulting
Wasm. Keep builds non-interactive and reproducible, minimize dependencies, and
test installation by tag and by immutable commit. Bloom records the resolved
commit but does not sandbox the source build in this iteration.
