# Writes And Receipts :badge[Partial]{warning}

Petals expose side effects as writable files. This page covers what a write
means, what it does not mean, and how to represent approval, submission,
broadcast, confirmation, and completion so that people and agents can tell them
apart.

## What a write is

A writable route exports `write`:

```wit
export write: func(ctx: ctx, body: list<u8>) -> result<_, route-error>;
```

Bloom waits for that export to complete and propagates its error to the VFS
caller, so a returned write error is visible to a mounted filesystem or a
`bloom vfs write` client. Design and test every write against synchronous
execution.

A writable route must define both handlers in its route file. Use the read
handler for safe instructions or current non-secret state, so the file is
discoverable and safe to `cat` before writing to it.

### `write_async` is reserved

The WIT `route-meta` record retains `write-async` for serialized-format
compatibility, and generated metadata and installation consent may call the same
field `write_async`. It is reserved metadata in this iteration: Bloom does not
detach writes when it is `true`, and authors must not document it as a
background-job guarantee. Set it deliberately only for compatibility with
existing components.

## What a write is not

A successful return means the route handler completed. It does **not** imply
that a transaction the handler staged has been approved, signed, broadcast, or
confirmed, or that a venue filled an order.

Never report a broadcast, confirmation, or fill solely because a route write was
accepted. Represent those states explicitly through inspectable routes and
receipts.

## The lifecycle

Keep these stages distinct in your durable state and in your `AGENTS.md`:

| Stage | Meaning |
| --- | --- |
| Accepted | The `write` export parsed and validated the body and returned success. |
| Staged | An intent or transaction exists and is durable, but no authority has been applied. |
| Approved | The owner completed the required Bloom approval ceremony. |
| Submitted | Bloom signed and handed the payload to an upstream or the outbox. |
| Broadcast | The transaction reached the network. |
| Confirmed | The network or venue durably accepted it. |
| Completed | The domain-level outcome occurred (filled, settled, transferred). |

For side-effecting routes:

- validate body size and shape before doing any external work;
- bind the body to the route's permitted operation — a route named for one
  action must reject a body describing another;
- preserve stable idempotency identifiers across approval retries;
- store enough status, response, and error state for inspection;
- make writes idempotent wherever retry is possible.

Do not exercise production writes or material funds unless the user explicitly
authorizes that environment and action.

## Binding the body to the route

The route file owns the check that the submitted body matches the file the
caller wrote to:

```rust title="route/files/.../order.json.rs"
write: |ctx: &petal::Ctx, body: &[u8]| {
    if let Err(response) = crate::validate_body_size(body) {
        return response;
    }
    let request = match crate::serde_json::from_slice::<crate::SignSubmit>(body) {
        Ok(request) => request,
        Err(error) => return petal::error(-3, format!("invalid session action: {error}")),
    };
    if !matches!(&request.action, crate::ExchangeAction::Order { .. }) {
        return petal::error(
            -3,
            format!("order.json cannot submit action type {}", request.action.kind()),
        );
    }
    crate::session_action_write(ctx, /* ... */ request)
}
```

## Signing and approvals

Petals never hold or manage private keys and never broadcast directly. A signing
route declares an intent through `signing_write_spec(intent)`; that intent must
appear in `[sign].allowed_intents` in `petal.toml`. Bloom owns the approval
ceremony and the signature.

For bounded delegated sessions, key derivation and signing are separate
authorities. A route that imports `bloom:key/derive@0.1.0` must declare the
child-key operation classes it delegates in `[[key.derive]]`, and each of those
classes must also be an allowed signing intent. The installer records only the
route's immediate intent plus those explicit delegated classes.

In the Hyperliquid Petal, session key provisioning takes two Bloom authority
steps: the key-derivation custody ceremony, and one reusable Sealed Approval
covering the typed session-action routes declared in the immutable key scope.
The approval binding is stored with the public `KeyRef`; each typed action
selects the same key and therefore reuses the approval without another owner
ceremony. Bounded agent private keys remain exclusively in Signer — the Petal
persists only the public `KeyRef` and EVM address, and private keys are never
generated by, returned to, or stored by the Petal.

## Receipts

Mutable "last response" files race. When a caller needs to confirm that one
specific action was accepted, give it an immutable receipt keyed by a
caller-supplied idempotency identifier.

Hyperliquid writes action receipts keyed by client order ID under the session:

```text
receipts/<cloid>/order.json
receipts/<cloid>/cancel.json
```

Each receipt is scoped by session, action, and normalized `cloid`, records the
original batch item and its index, and contains only that item's positional
venue status — so it cannot be overwritten by a later action or raced against
the session's mutable `last_response.json`.

A route's read handler should tell callers how to recognize completion: the
receipt path, a poll interval, a timeout, and the exact predicate that
constitutes success. Document that an accepted filesystem write is asynchronous
with respect to the venue and that dispatch may take longer than the caller
expects — the correct behavior is to keep polling the exact receipt path for the
full timeout, not to assume success.

## Inspecting from the filesystem

Because everything is a file, the whole lifecycle is inspectable with ordinary
tools:

```sh
bloom vfs cat  /petals/hyperliquid/mainnet/agent_sessions/w1/s1/order.json
bloom vfs write /petals/hyperliquid/mainnet/agent_sessions/w1/s1/order.json < order.json
bloom vfs cat  /petals/hyperliquid/mainnet/agent_sessions/w1/s1/status.json
bloom vfs cat  /petals/hyperliquid/mainnet/agent_sessions/w1/s1/last_error.json
bloom vfs cat  /petals/hyperliquid/mainnet/agent_sessions/w1/s1/receipts/0x…/order.json
```

Reading the writable route first returns its request schema, an example body,
and its success-evidence contract. Test both the direct VFS fallback and a
mounted daemon before publishing — see [Testing](/petals/testing).
