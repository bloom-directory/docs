# Quickstart :badge[Partial]{warning}

This guide scaffolds a Petal, builds its route components, validates the
package, and installs it into walletFS.

## Prerequisites

Install the Petal CLI. It provides the `petal` binary:

```sh
cargo install bloom-petal-cli
```

You also need a `bloom` binary for package validation and installation. Public
installation packaging is still TBD; for now, use whichever Bloom binary your
network or operator provides.

Confirm which contract release your toolchain speaks:

```sh
petal inspect
```

This prints the canonical contract version and its WIT digest. Consumer CI
should reject a digest it did not intentionally upgrade to.

## Scaffold

```sh
petal new my-petal ./my-petal
```

The command refuses an existing destination — it will not overwrite a
repository with a fresh scaffold. It generates:

```text
my-petal/
  petal.toml
  petal-build.toml
  README.md
  AGENTS.md
  route/
    Cargo.toml
    src/lib.rs            # shared domain code
    files/
      status.json.rs      # one route file -> one component
  scripts/
    check-route-architecture.sh
```

`README.md` is developer and contributor documentation. `AGENTS.md` is the
operating contract for users and agents: it documents paths, input bodies, side
effects, approval steps, idempotency, and how to recognize completion.

## The two manifests

`petal.toml` is the package manifest that Bloom validates and installs:

```toml title="petal.toml"
schema = "bloom.petal.package.v1"
name = "my-petal"

[consent]
summary = "Example read-only Petal generated by petal new."

[caps]
allowed = []
```

`name` must equal the sole directory under `petal/`. It may contain ASCII
letters, digits, `-`, and `_`; it may not contain dots or Unicode. Bloom mounts
`petal/my-petal/` at `/petals/my-petal/`.

`petal-build.toml` drives the route builder:

```toml title="petal-build.toml"
schema = "bloom.petal.build.v1"
name = "my-petal"
routes = "route/files"
output = "petal/my-petal"

[route_crate]
package = "my-petal-route"
path = "route"
alias = "example_route"

[sdk]
package = "bloom-petal-sdk"
version = "=0.1.0"

[dependencies]
serde_json = "1"
```

## Your first route

Every `.rs` file under the configured `routes` directory becomes a separately
compiled component. The scaffold's route is a static read:

```rust title="route/files/status.json.rs"
petal::route_file!(
    spec: petal::static_read_spec(),
    read: |_ctx: &petal::Ctx| petal::read_json_value(&serde_json::json!({
        "petal": "my-petal",
        "status": "ok"
    }))
);
```

Add a directory listing so the route is discoverable, and a dynamic route that
reads a path parameter:

```rust title="route/files/$index.rs"
petal::route_file!(
    spec: petal::static_dir_spec(),
    list: petal::files(&["status.json"])
);
```

```rust title="route/files/items/[id].json.rs"
petal::route_file!(
    spec: petal::static_read_spec(),
    read: |ctx: &petal::Ctx| {
        let id = match petal::param(ctx, "id") {
            Ok(id) => id,
            Err(response) => return response,
        };
        if !petal::is_safe_segment(id) {
            return petal::error(-3, "invalid item id");
        }
        petal::read_json_value(&serde_json::json!({ "id": id }))
    }
);
```

Directory contents are explicit — listing a dynamic directory does not happen
automatically. See [Authoring](/petals/authoring) for the full set of route
shapes and specs.

## Build and check

```sh
bash scripts/check-route-architecture.sh
cargo test --manifest-path route/Cargo.toml --locked
petal build --root .
petal check --root .
```

`petal build` compiles every route file into a component under the configured
output. `petal check` reconciles each route's declared capabilities against the
imports of the components that were just built; it does not rebuild, so never
run it against stale artifacts.

A successful `cargo build` of the shared route crate is **not** evidence that
your route sources compile. Route files are independently generated component
crates and only `petal build` exercises them.

## Validate and install with Bloom

`petal` validates components. `bloom` validates the complete package policy:

```sh
bloom petals build .
bloom petals install .
```

`bloom petals build` can also emit a deterministic uncompressed archive, and
`bloom petals install` accepts a directory, a `.petal.tar`, or a trusted GitHub
source repository URL:

```sh
bloom petals build . --out my-petal.petal.tar
bloom petals install my-petal.petal.tar
```

Then exercise the mounted tree:

```sh
bloom vfs ls /petals/my-petal
bloom vfs cat /petals/my-petal/status.json
bloom vfs cat /petals/my-petal/README.md
```

`bloom petals ls` lists installed Petals; `bloom petals uninstall` removes one
by content hash, name, or petname.

## Package for release

`petal package` writes the platform-neutral archive Bloom consumes:

```sh
petal package --root . --out dist/my-petal-v0.1.0.petal.tar.gz
```

It checks every built component before writing. The archive uses sorted strict
ustar entries with normalized ownership, permissions, and timestamps, and a
gzip header with a zero timestamp, so repeating the command over the same clean
package tree produces identical bytes. It refuses to overwrite an existing
output. Generated `.git`, `.jj`, `target`, and `artifacts` trees are excluded.

Publish with the reusable release workflow from `bloom-directory/petal`, pinning
both the workflow and the tooling input to the same reviewed 40-character
commit SHA. For Petal `example` at tag `v0.1.0` it publishes three immutable
assets in your repository:

- `example-v0.1.0.petal.tar.gz`
- `SHA256SUMS`
- `petal-release.json`

`petal-release.json` uses schema `bloom.petal.release.v1` and binds the Petal
name, caller repository, exact source commit, release tag, archive filename and
SHA-256, Bloom package hash, and the exact Petal tooling commit — so Bloom can
pin and verify a release without cloning or building the source.
