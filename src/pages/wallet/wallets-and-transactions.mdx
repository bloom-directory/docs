# Wallets and transactions :badge[Partial]{warning}

Bloom wallets are Broker-projected HD identities. Signer retains the seed-derived private keys; Machine exposes public account inventory, policies, approvals, balances, and outbox state through the filesystem. Machine never creates or opens a local keystore.

## Register a wallet

Writing a petname starts an asynchronous Broker custody operation:

```sh
printf 'alice\n' > /bloom/wallets/new
cat /bloom/wallets/registrations/alice/status.json
```

Verify that `requested_name` is `alice` before opening its single-use `ceremony_url`, polling it, or cancelling it. Complete the passkey ceremony and wait for `ceremony_state` to become `COMPLETED`.

## Use a numbered HD account

A wallet's root shows its authenticated account inventory. Chain keys and transaction routes are deliberately not exposed at the wallet root: choose the numbered account that will own the action.

```sh
cat /bloom/wallets/alice/accounts.json
cat /bloom/wallets/alice/0/account.json
cat /bloom/wallets/alice/0/address.evm
cat /bloom/wallets/alice/0/address.sol
cat /bloom/wallets/alice/0/chains/anvil/balance.json
```

`account.json` records the public account identity, including available EVM and Solana keys, their fingerprints, and derivation paths. Account-scoped paths prevent an agent from silently selecting a different derived key.

Create another derived account through the wallet's account-creation control, then read `accounts.json` again to obtain its number before using it:

```sh
printf '%s\n' '<request_id>' > /bloom/wallets/alice/new
cat /bloom/wallets/alice/accounts.json
```

Import, recovery, credential changes, and deletion also use Broker-hosted custody ceremonies. Never put a private key, passkey output, mnemonic, or recovery secret in a mounted file, command argument, environment variable, or agent prompt.

## Stage an EVM intent

```sh
echo 'send 0.01 eth to 0x70997970C51812dc3A010C7d01b50e0d17dc79C8 on anvil' \
  > /bloom/wallets/alice/0/chains/anvil/outbox/new.tx
```

Machine parses the intent, fills public defaults, simulates where possible, and creates a pending directory.

## Stage a native Solana transfer

Solana transfers use the same account-scoped outbox lifecycle. The initial native-transfer surface accepts strict JSON with a base58 destination and an amount in lamports. When a wallet has multiple active Solana children, bind the transfer to one with `account_fingerprint`.

```sh
cat > /tmp/sol-transfer.json <<'EOF'
{"destination":"<base58-public-key>","lamports":1000000,"account_fingerprint":"<fingerprint>"}
EOF
cp /tmp/sol-transfer.json \
  /bloom/wallets/alice/0/chains/solana-mainnet/outbox/new.tx
```

Bloom verifies the configured cluster genesis hash before staging and broadcasting. A staged transfer carries the exact message, fee quote, blockhash, and validity height. If its blockhash expires, restage it; approval and signatures are never reused for a replacement.

## Review, approve, and confirm

```sh
ls /bloom/wallets/alice/0/chains/anvil/outbox/pending
cat /bloom/wallets/alice/0/chains/anvil/outbox/pending/<id>/plan.md
cat /bloom/wallets/alice/0/chains/anvil/outbox/pending/<id>/policy_check.json
printf 'confirm\n' > /bloom/wallets/alice/0/chains/anvil/outbox/pending/<id>/confirm
```

If Broker requires fresh owner approval, the confirm fails closed after projecting `approval_challenge.json`. Read it from that exact action, verify the action ID, review digest, and expiry, then deliberately open or forward its `ceremony_url`.

After the ceremony completes, retry the same confirm. Broker authorizes the exact payload, Signer checks the account key scope and approval bindings, and Machine broadcasts when the chain permits it. Browser completion never broadcasts by itself.

Successful entries move to `outbox/sent/<id>/`; terminal failures are projected under `outbox/failed/<id>/`. For Solana, `sent` means a submission may have been attempted; read the receipt and reconciliation result rather than treating it as finality.

## Policy updates

`/bloom/wallets/<wallet>/policy.json` is the complete canonical writable policy. Preserve the exact proposal bytes across the ceremony:

```sh
cat /bloom/wallets/alice/policy.json > proposed-policy.json
# Edit the complete JSON document.
cp proposed-policy.json /bloom/wallets/alice/policy.json
cat /bloom/wallets/alice/policy-updates/latest/status.json
cat /bloom/wallets/alice/policy-updates/latest/approval_challenge.json
# Complete the policy_update custody ceremony, then retry identical bytes.
cp proposed-policy.json /bloom/wallets/alice/policy.json
```

Broker validates the proposal and exact review; Signer commits it with an authenticated compare-and-swap only after the custody receipt is complete.

## Reusable authority

Sealed Approvals are durable, bounded Broker/Signer authority. Public preparation, status, limits, renewal, and revocation projections live under:

```txt
/bloom/wallets/<wallet>/sealed-approvals/
```

An approval binds a key, exact payload or installer-pinned Petal scope, allowed operations and suites, limits, policy, expiry, and revocation. Machine's projection is not itself authority.
