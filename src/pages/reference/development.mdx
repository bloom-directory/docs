# Development :badge[Shipped]{success}

## Build

```sh
cargo build --workspace
cargo build -p bloom --no-default-features
cargo build -p bloom --no-default-features --features mount
```

`bloom` builds the key-free Machine CLI/runtime. Broker and Signer live in the sibling `bloom-broker` and `bloom-signer` repositories and must be built and tested there. Machine must never connect directly to Signer or compile a local authority fallback.

## Run the separate-process profile

Use the developer launcher documented in [Local build and mount](/integrators/quickstart). It starts real Machine, Broker, and Signer protocol implementations as separate processes and writes public connection settings to its selected log directory.

After sourcing the generated `triad.env` in a second shell, commands such as `bloom status`, `bloom wallet new`, and `bloom vfs` proxy to the running Machine. Only `bloom init` and `bloom serve` own local Machine lifecycle; other commands do not construct a one-shot runtime.

```sh
source /tmp/bloom-triad-logs/triad.env
bloom status
bloom vfs cat /status/daemon.json
bloom wallet new test-wallet
```

## Test

```sh
cargo fmt --all -- --check
cargo check --workspace --all-targets --locked
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
packaging/triad/release/check-machine-authority-boundary.sh
packaging/triad/release/test-machine-authority-boundary.sh
```

Run the relevant protocol and transport suites in `bloom-broker` and `bloom-signer` for cross-edge changes. macOS packaging and principal isolation require the disposable Tart/W0 workflow; do not infer production conformance from the same-UID developer launcher.

## Formatting and linting

Use the Rust toolchain pinned in the Bloom repo. Run the narrow test first for the area you changed, then broader workspace or Docker checks before release.
