# Technical architecture :badge[Partial]{warning}

Bloom's filesystem-facing runtime is the **Machine** in a separate-process authority architecture. Machine handles public data and execution, Broker handles policy and authorization, and Signer alone holds keys and signs. See [Triad Architecture](/reference/triad-architecture) for the security protocol and platform isolation model.

## Runtime shape

```txt
agent, shell, or application
    │
    ├─ mounted filesystem: /bloom
    │     ├─ reads:  ls /bloom/chains, cat /bloom/status/daemon.json
    │     └─ writes: echo ... > /bloom/wallets/<name>/chains/<chain>/outbox/new.tx
    │
    ▼
Machine (bloom serve)
    ├─ VFS router and NFS adapter
    ├─ unsigned transaction construction, simulation, execution, and broadcast
    ├─ chain RPC, metadata, watches, tools, and installed Petal host
    ├─ public wallet, policy, approval, audit, and result projections
    └─ authenticated local RPC ──▶ Broker ──▶ Signer
```

`bloom serve --mount /bloom` owns the long-running Machine. Other CLI commands and the `bloom vfs` facade proxy to that running process; they do not construct a one-shot Machine or embed a custody fallback.

Machine may cache authenticated public projections, but those files are not authority. Wallet keys, credential secrets, approval state, canonical policy custody, and signing remain outside Machine.

## NFS mount surface

Bloom exposes the VFS over NFS v4.1. The local mount is the ordinary filesystem surface backed by Machine's router, handlers, planning, and result projections. It supports normal Unix tooling and makes the same path contract available to agents, shells, containers, VMs, and other local processes.

The mount's OS permissions remain part of the boundary. Production packaging scopes Machine to an enrolled login and places Broker and Signer behind separate authenticated service principals and local transports.

## Main Machine components

| Component | Responsibility |
| --- | --- |
| `bloom` | CLI and Machine lifecycle; all non-lifecycle commands proxy to the running Machine. |
| `bloom-daemon` | Wires key-free Machine state, config, chain services, VFS, IPC, ENS, watches, and execution adapters. |
| `bloom-machine-client` | Authenticated Machine-to-Broker client and rollback-safe public projection cache. |
| `bloom-vfs` | Path router, handlers, public projections, vendored docs, and mounted action surfaces. |
| `bloom-tx` | Unsigned transaction staging, simulation, Broker signing orchestration, broadcast, and nonce management. |
| `bloom-evm` / `bloom-rpc` | EVM chain reads, RPC pools, endpoint health, and failover. |
| `bloom-petals` | Installed Petal host, package validation, route execution, and payload-bearing signing bridge. |
| `bloom-paid-http`, `bloom-paid-x402`, `bloom-paid-mpp` | Free and paid HTTP planning and protocol handling. |
| `bloom-watch` | Subscription registry and polling executor. |
| `bloom-mount` | NFSv4 adapter that mounts Machine's VFS. |
| `bloom-tools` | Hashing, encoding, ABI, RLP, unit, and EIP-712 helpers. |
| `bloom-etherscan`, `bloom-ens`, `bloom-prices` | Indexed metadata, ENS, and price integrations. |
| `bloom-proto` | Shared public config, audit, intent, policy, plan, path, and protocol types. |

## Data flow for a transaction

1. The agent writes an intent to a wallet outbox path.
2. Machine parses it, resolves public inputs, constructs unsigned bytes, and simulates where possible.
3. Machine creates a pending directory with the intent, `plan.md`, policy/status projections, and control files.
4. On confirmation, Machine asks Broker to authorize the exact operation.
5. If fresh approval is required, Broker returns an action-bound `approval_challenge.json` containing the review identity, expiry, and single-use ceremony URL.
6. The user completes the Broker-hosted ceremony; Signer independently verifies it. No broadcast occurs in the browser.
7. The client retries confirmation. Broker evaluates policy and asks Signer to sign the exact payload.
8. Signer enforces key scope, approval bindings, counters, expiry, revocation, and replay before returning a signature and receipt.
9. Machine broadcasts when chain routing permits and moves the entry to `sent/` or `failed/`.

## Backend and failure boundaries

Some reads use direct RPC; address history and contract metadata use Etherscan where configured. Current backend declarations are exposed under `/bloom/status/backends/`.

If Broker is unavailable, cached public reads, unsigned staging, and simulation may continue. Signing, approval mutation, policy mutation, and custody fail promptly. Signer unavailability prevents custody and signatures. Neither failure activates a legacy keystore, local approval store, raw hash-signing route, or direct Machine-to-Signer edge.
